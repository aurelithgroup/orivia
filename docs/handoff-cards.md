# Show someone and map handoffs

Private pilot feature. No new service, key, location permission, or automatic transmission.

When Orivia suggests showing a request to a person, the assistant returns `showMessage: {texts: {en, ar, <reply_language>}}`. These are generated in the existing answer call. They must be equivalent, short requests using only volunteered chat details and relevant sourced public facts. The server requires each requested language and checks numeric/contact/link facts against the user's conversation and fetched evidence. This is not a semantic translation guarantee; real language review is still required. No saved profile is separately sent for this feature. Displayed messages persist with the chat on this device, like drafts; they are not added to future chat text.

The inline card previews the user's language and says to review before showing it. Tapping **Show someone** opens a native modal with English, Arabic and the selected app language (without duplicates). The modal shows only the selected message, not the conversation or source panel. Language changes stop speech. Listen uses an explicit language rather than guessing French/English from Latin letters. Closing, including Escape, stops speech and restores focus. Missing device voices produce a visible message rather than reading in another language. There is no automatic speech, clipboard operation, message send or share.

Destinations are `{name, address, evidence}` in the assistant's answer. Name and address must appear on the same fetched official record or qualifying organisation page. The server drops unsourced addresses and listing-only records, and returns a source ID and supporting passage. Website destinations additionally need an organisation-name token in the host (a conservative heuristic, not proof of ownership). It can miss operator/group-owned sites. Cards never imply that a page establishes website ownership.

The client builds encoded Google Maps and Apple Maps **search** URLs from the approved name/address. It does not accept model-generated map URLs, coordinates or a starting location. A note asks the person to check the place and entrance before directions. Nothing is sent to either map provider until a link is tapped. App-versus-browser routing depends on the device. These are not live routes, geolocation, or embedded maps. Those remain later work.

Tests: `tests/handoff-cards.test.mjs` covers missing translations, invented translated numbers, unsourced/listing/unrelated destinations, source mapping, encoded links, language/direction switching, explicit speech language, no automatic playback, close/focus, and one scripted assistant turn. Full-browser checks use clearly labelled fixture data, not live research. Real phone handoff/audio and live model generation remain manual checks.

## Visual destination cards

The place card now has a hero, large name/address, optional description and up to three relevant details, an amber **Take me there** button, and a heart **Save** button. Details and description are retained only when they are contiguous passages on the same destination source page. Missing information is omitted. The map button expands a choice of Apple/Google Maps; it does not embed a map or claim a route/entrance is verified.

Save marks that destination within the existing chat, and **My Life → Saved places** links back to it. Removing a save does not delete the conversation. Deleting a chat removes its saved-place marks. Storage is device/browser only; the existing full-device warning applies. Saving failure says **Not saved yet**.

An optional website image preview is discovered from `og:image`/`twitter:image` on a page already fetched for the destination. Only the same HTTPS origin is used; redirects, credentials, SVGs, wrong raster signatures, excess size and timeouts are rejected. At most one preview per reply, 120 KB maximum, with a 1.5-second timeout. The raster is returned inline as a data image, stored with the chat, and never sent to the model/search provider. The browser makes no request to an image host. CSP adds only `img-src data:` on the private page; other policy directives are preserved. This may add up to 1.5 seconds for an eligible photo. CDN-hosted or larger photos are omitted, and earlier memory-only sources may not have an image. A preview supplied by a site is not proof of which entrance it shows or independent proof of identity. No generated or generic photograph is substituted; a navy/amber pin illustration is the fallback.

`tests/place-card.test.mjs` covers raster origin/type/signature/size/redirect failures, details, chooser, save/reload/My Life and illustration fallback. Browser visual checks use clearly marked sample data and a photo already in the repo. Actual live source/photo availability and phone map-app handling still require real use.

## Trips in the private assistant

The consented private assistant now receives route requests rather than being bypassed for recognised trips. The old route planner remains for basic-mode fallback. User-stated origin and explicit travel mode are carried into the destination card when the checked destination matches the trip. Merely naming a metro station as an origin does not choose public transport. Car/driving requests skip the old time/cost/reliability question; short duration follow-ups retain the trip. The map card uses directions URLs with the selected mode rather than a destination search. Apple cycling is not offered because this integration has no confirmed cycling handoff; Google preserves that mode.

The existing official university registry is also accepted as the tie between a known institution name and its abbreviated official host (for example Heriot-Watt and hw.ac.uk); the destination name still has to occur in fetched evidence. This does not accept arbitrary similar hosts. Orivia has no traffic/routing-time feed and must not invent ETAs, distances or turn-by-turn instructions. The start point is as the person typed it, not independently located or checked.

`tests/transport-assistant-card.test.mjs` replays the Heriot-Watt/Al Garhoud/by-car case through a scripted assistant and the real private route handler. It checks assistant routing, retained origin/mode, the registered official host, and both driving map URLs. This is not a live routing or live-model test.
