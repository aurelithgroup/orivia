# Show someone and map handoffs

Private pilot feature. No new service, key, location permission, or automatic transmission.

When Orivia suggests showing a request to a person, the assistant returns `showMessage: {texts: {en, ar, <reply_language>}}`. These are generated in the existing answer call. They must be equivalent, short requests using only volunteered chat details and relevant sourced public facts. The server requires each requested language and checks numeric/contact/link facts against the user's conversation and fetched evidence. This is not a semantic translation guarantee; real language review is still required. No saved profile is separately sent for this feature. Displayed messages persist with the chat on this device, like drafts; they are not added to future chat text.

The inline card previews the user's language and says to review before showing it. Tapping **Show someone** opens a native modal with English, Arabic and the selected app language (without duplicates). The modal shows only the selected message, not the conversation or source panel. Language changes stop speech. Listen uses an explicit language rather than guessing French/English from Latin letters. Closing, including Escape, stops speech and restores focus. Missing device voices produce a visible message rather than reading in another language. There is no automatic speech, clipboard operation, message send or share.

Destinations are `{name, address, evidence}` in the assistant's answer. Name and address must appear on the same fetched official record or qualifying organisation page. The server drops unsourced addresses and listing-only records, and returns a source ID and supporting passage. Website destinations additionally need an organisation-name token in the host (a conservative heuristic, not proof of ownership). It can miss operator/group-owned sites. Cards never imply that a page establishes website ownership.

The client builds encoded Google Maps and Apple Maps **search** URLs from the approved name/address. It does not accept model-generated map URLs, coordinates or a starting location. A note asks the person to check the place and entrance before directions. Nothing is sent to either map provider until a link is tapped. App-versus-browser routing depends on the device. These are not live routes, geolocation, or embedded maps. Those remain later work.

Tests: `tests/handoff-cards.test.mjs` covers missing translations, invented translated numbers, unsourced/listing/unrelated destinations, source mapping, encoded links, language/direction switching, explicit speech language, no automatic playback, close/focus, and one scripted assistant turn. Full-browser checks use clearly labelled fixture data, not live research. Real phone handoff/audio and live model generation remain manual checks.
